## 工作分解

### Step 1: API Key 认证（1-2 天）
- `internal/config/config.go`：新增 `APIKeys []APIKeyConfig`
- `internal/middleware/apikey.go`：Bearer token 校验，与 BasicAuth 并行
- ~~`mibee-nvr generate-api-key` CLI 子命令~~ **（未实现/弃用）**：无此 CLI 子命令；API Key 经 `POST /api/settings/api-keys`（返回一次 `mbv_<40hex>`）或 Web UI 设置页生成。
- 设置页 API Key 管理 UI（生成/列表/撤销）

### Step 2: 事件增强（1 天）
- `internal/event/types.go`：SegmentCompleted 加 Encoding 字段 ✅ **（已实施）**
- ~~FilePath 改相对路径~~ **（未实施）**：`file_path` 仍是绝对路径（`storage.Manager` 用 `filepath.Join(rootDir,...)` 构造）。设计意图未落地，详见 interaction-protocol.md §三。
- `internal/event/types.go`：新增 SegmentDeleted 事件类型 ✅
- `internal/cleanup/`：删除录像时发布 segment.deleted ✅
- SSE `GET /api/events` 支持新事件类型 ✅

### Step 3: AI 事件回写（3-4 天）
- `internal/storage/db.go`：ai_events 表 migration ✅
- `internal/storage/db_ai.go`：AI 事件 CRUD ✅
- `internal/api/handlers_ai.go`：POST/GET /api/ai/events ✅
- ~~snapshot 服务~~ **（未实现）**：无 `GET /api/ai/events/{id}/snapshot` 路由；`snapshot_path` 存于 DB 但无独立 serving 端点。
- 前端：AI 事件列表页 + 时间线视图 + 快照展示 ✅
- Metrics: `nvr_ai_events_received_total{camera_id,event_type}` ✅

### Step 4: 录像操作接口（2-3 天）
- `internal/api/handlers_recording.go`：扩展 POST/PATCH/DELETE 支持外部写入 ✅
- 审计字段 `modified_by`
- DELETE 软删除（archived 标记）
- ~~`PUT /api/recordings/{id}/file`：文件替换（原子操作）~~ **（未实现）**：见 future-design.md 域 8。

### Step 5: 处理状态（1-2 天）
- `internal/storage/db.go`：recordings 表加 ai_status / ai_processed_at / ai_error ✅
- `PATCH /api/recordings/{id}/ai-status` ✅（合法值 `pending`/`processing`/`completed`/`failed`）
- `internal/cleanup/`：跳过 processing 状态的录像 ✅

## 测试策略
- 每个接口用 mock MiBeeVision 客户端做集成测试
- API Key 认证：合法/非法/过期/撤销
- SSE 事件：segment.completed/deleted 格式验证
- 并发写：MiBeeVision 写 + 用户操作的冲突处理
